Use this as a reference guide for hackathon demos and technical interview talking points.🗄️ 1. Chunking Strategy & RationaleStrategy: Atomic Document Mapping (1-FIR-to-1-Chunk).Configuration: chunk_size=1024, chunk_overlap=0 (enforced via LlamaIndex SentenceSplitter).Why We Avoided Standard Sliding Windows:Legal documents like FIRs rely heavily on interconnected, holistic context. Standard recursive text splitting (e.g., breaking text every 200 words) risks severing critical relationships—such as separating a suspect's vehicle description in paragraph one from the stolen item listed in paragraph three. Because our synthetic FIR narratives are concise and fit safely within standard context windows, mapping one full legal incident to exactly one vector embedding guarantees total context retention.Interview Talking Point: We intentionally bypassed standard fixed-size sliding-window chunking. In legal intelligence, context fragmentation is a critical failure point. By ensuring one entire FIR maps to one vector, we ensure that suspect descriptions, timestamps, and stolen property remain unified in the embedding space.🧠 3. Embedding Model Selection (LaBSE)Model: sentence-transformers/LaBSE (Language-agnostic BERT Sentence Embedding)Vector Dimensions: 768Architectural Trade-offs Evaluated:vs. bge-small (384-dim): While bge-small is incredibly fast and lightweight, it is fundamentally restricted to English semantics. It failed completely when handling native Indic inputs.vs. paraphrase-multilingual-mpnet-base-v2: mpnet performs well across European languages but exhibits semantic drift on low-resource Dravidian languages.Why LaBSE Won: Engineered specifically by Google for massively multilingual and cross-lingual vector mapping. It embeds English text and Kannada queries into the exact same shared vector space. This allows a user to query the system in Kannada and retrieve the closest semantic English matching record natively, without spinning up an intermediate, high-latency translation API layer.🚀 4.
